# Automated package update plan

The goal is to make upstream refreshes mechanical and reviewable without
turning `guix refresh` into a build system.  `guix refresh` remains the
version detector; a small update framework owns the package-specific work:
pin edits, lock regeneration, exception updates, verification and PR
publication.

## Design principles

- **Detect, prepare and verify are separate jobs.**  Detection needs no
  network secrets.  Preparation needs network but no signing key.  Verification
  is offline.  Publication owns the signing key.
- **Generated files are never hand-edited.**  Version/source pins and lock
  closures are outputs of an adapter; package recipes consume them.
- **One package or product line per change.**  Kilocode, opencode-v1 and
  opencode-v2 are separate units even when they share an upstream repository.
- **Autonomy is opt-in per package.**  A package declares whether it may only
  be detected, may get a PR, or may auto-merge patch/minor updates.
- **No build script runs during detection.**  `bun install`, `cargo update`,
  Go module resolution and native-payload inspection happen only in the
  isolated prepare job.
- **The final build is offline.**  `guix build --no-substitutes` is the
  hermetic check; substitutes may be used earlier to warm the store.

## Autonomy levels

| Level | Behaviour |
|---|---|
| L0 | Detect only; precompiled/exception packages and manual recipes. |
| L1 | Detect and open an issue, no patch. |
| L2 | Update pin/source hash, open a PR; human runs/reviews locks. |
| L3 | Update pin, regenerate locks, update exceptions/docs, open a verified PR. |
| L4 | L3 plus auto-merge for patch/minor updates after all gates pass. |

Most packages should start at L2.  Kilocode/opencode should reach L3 before
considering L4.  Precompiled packages (Ghidra, Electron, Bun bootstrap) stay at
L0/L1.

## Components

### 1. Update manifest

`planning/update-manifest.json` is the machine-readable inventory.  It should
describe *how* to update a package, not repeat the package recipe.

```json
{
  "kilocode": {
    "module": "kilocode",
    "package": "kilocode",
    "repo": "kilo-org/kilocode",
    "tag_regex": "^v[0-9]",
    "pin": "modules/under-sea/packages/kilocode-pin.scm",
    "adapter": "bun",
    "bun": "bun-for-hermes",
    "lock": {
      "script": "scripts/lock-kilocode.py",
      "output": "modules/under-sea/packages/kilocode-lock.scm"
    },
    "tests": ["make kilocode", "make verify-phase7"],
    "autonomy": "L3"
  },
  "opencode-v1": {
    "module": "opencode-v1",
    "package": "opencode-v1",
    "repo": "anomalyco/opencode",
    "tag_regex": "^v1\\.",
    "pin": "modules/under-sea/packages/opencode-v1-pin.scm",
    "adapter": "bun",
    "bun": "bun-for-opencode",
    "lock": {
      "script": "scripts/lock-opencode.py",
      "module": "(under-sea packages opencode-v1-lock)",
      "prefix": "opencode-v1",
      "output": "modules/under-sea/packages/opencode-v1-lock.scm"
    },
    "tests": ["make opencode-v1", "make verify-phase7"],

  },
  "opencode-v2": {
    "module": "opencode-v2",
    "package": "opencode-v2",

    "adapter": "bun",
    "bun": "bun-for-opencode",
    "lock": {
      "script": "scripts/lock-opencode.py",
      "module": "(under-sea packages opencode-v2-lock)",
      "prefix": "opencode-v2",
      "output": "modules/under-sea/packages/opencode-v2-lock.scm"
    },

    "autonomy": "L3"
  }

```

The manifest is also the source for the CI matrix and the update report.

### 2. Pin modules

Move volatile data out of recipes:

```scheme
;;; Generated by scripts/update/prepare.py; do not edit.
(define-public %kilocode-version "7.8.12")
(define-public %kilocode-source
  (origin
    (method url-fetch)
    (uri "https://codeload.github.com/kilo-org/kilocode/tar.gz/refs/tags/v7.8.12")
    (file-name "kilocode-7.8.12.tar.gz")
    (sha256 (base16-string->bytevector "..."))))
```

The recipe imports the pin module.  This lets the updater rewrite data without
parsing or reformatting Scheme build logic.  Packages that still keep pins
inline are migrated incrementally; the adapter has a fallback that edits
`version`, `uri`, `file-name` and `sha256` in place.

### 3. Adapters

An adapter is a Python module under `scripts/update/adapters/` implementing a
small protocol:

```text
detect(manifest) -> {current, latest, tag, notes}
prepare(manifest, version, workdir) -> patch files + metadata
verify(manifest, workdir) -> commands to run
```

Adapters can share primitives:

- `github.py`: tags/releases, tag-regex filtering, codeload tarball, sha256.
- `pypi.py`: sdist selection and hash.
- `bun.py`: run `bun install --frozen-lockfile`, capture the install cache,
  invoke a lock script, and inventory native payloads.
- `cargo.py`: run the existing Cargo lock inventory scripts.
- `go.py`: run the existing Go module lock scripts.
- `exceptions.py`: diff native payloads against
  `planning/precompiled-exceptions.json`.
- `docs.py`: update version tables and lock counts from metadata.

The first adapters should be `github`, `bun` and `pypi`.  Existing lock scripts
stay authoritative; adapters only invoke them and validate their output.

### 4. Commands

A single entry point keeps CI and local use identical:

```sh
scripts/update/run.py detect --all --json
scripts/update/run.py detect --package kilocode --json
scripts/update/run.py prepare --package kilocode --version 7.8.15 --workdir /tmp/update
scripts/update/run.py verify --package kilocode --workdir /tmp/update
scripts/update/run.py report --json
```

`prepare` must be idempotent: if the pin already matches the requested
version, it exits without changes.  It must write a machine-readable
`update.json` containing old/new versions, source hash, lock origin delta,
exception delta and the exact test commands.

## CI pipeline

Use a self-hosted Guix runner (and a KVM-capable runner for VM tests).

```text
detect (scheduled/manual, no secrets)
  -> prepare (network, no signing key)
  -> verify (offline, Guix)
  -> vm (KVM, only packages with VM tests)
  -> publish (protected environment, signing key)
```

### detect

- Read `planning/update-manifest.json`.
- Query GitHub/PyPI with ETag/cache; respect rate limits.
- Emit a matrix of packages with `latest != current`.
- For opencode, apply `tag_regex`; do not rely on the shared upstream's
  `latest` release.
- Open/update a tracking issue when no automatic adapter exists.

### prepare

- Fetch the exact tag/commit and verify the tarball hash.
- Generate the pin module.
- Run the adapter's lock step in a network-enabled container:
  - Bun cache generation with the manifest's Bun package.
  - `lock-kilocode.py` / `lock-opencode.py`.
  - Validate zero failures and a plausible origin count delta.
- Update `planning/precompiled-exceptions.json` only when the native payload
  inventory changes; mark the PR for human review.
- Upload the patch, lock files, `update.json` and a test plan as artifacts.
- Never commit or sign here.

### verify

- Apply the artifact to a clean checkout.
- Run `guix build --no-substitutes` for the package.
- Run `make verify-standalone`, `scripts/verify-packaging.sh` and the
  package's declared host tests.
- Run dependent builds when the manifest declares them (for example
  `bun-for-opencode` → opencode v1/v2).

### vm

- Run only the declared VM tests, e.g. the opencode VM test.
- A KVM-less runner may skip, but the PR must record the skip explicitly.

### publish

- Protected environment with the signing key and a GitHub App token.
- Commit with `git commit -S`, one package per PR.
- PR body includes version, source hash, lock origin delta, exception delta,
  test results and skipped gates.
- Human merge by default.  L4 auto-merge is opt-in per package and only for
  patch/minor updates; major updates always require review.

## Security and correctness invariants

- Prepare and publish credentials are never in the same job.
- All source and lock origins are https with sha256; no `file:`/untrusted
  git URLs.
- Lock generation is deterministic: run the locker twice and compare output.
- The build job must not reach the network; use `--no-substitutes` for the
  final check.
- Precompiled payload changes always require human review.
- Update branches are force-pushed only by the bot; PRs are superseded, not
  duplicated.
- Do not auto-update pinned Guix channels; channel refreshes are a separate
  task.

## Acceptance criteria

- `scripts/update/run.py detect --all --json` produces a stable matrix without
  modifying the tree.
- A package can be updated from a manifest entry with no hand-edited Scheme
  beyond its adapter.
- Lock scripts are invoked by adapters, not reimplemented.
- A failed prepare/verify leaves no branch or PR.
- Every PR contains reproducible evidence: source hash, lock delta, exception
  delta and test results.
- Kilocode and opencode v1/v2 can be detected independently and produce
  separate verified PRs.
- The final verification build runs with network disabled.

## Known gaps to fix first

- The current `under-sea-github` updater has no tag filter; opencode v1/v2
  cannot be distinguished.  The manifest detector should handle this first.
- Kilocode/opencode pins are inline in recipes; migrate to `*-pin.scm`.
- README/STATUS versions drift (kilocode currently documents 7.8.8 while the
  package is 7.8.12); generate or check these from the manifest.
- There is no CI workflow yet; start with detect-only before adding prepare and
  publish.
